### 2026-06-17: Validate numeric factors before any DB read in geometry actions
tags: entities=inventory-item,spacing,geometry,server-action · files=apps/partner/app/sites/[id]/inventory/actions.ts,apps/partner/app/sites/[id]/inventory/actions.test.ts

**Problem:** `adjustItemSpacing(siteId, itemIds, axis, factor)` scales distances from the selection centroid. A `factor` of `0` collapses every item onto the centroid and a negative factor mirrors the layout — both overwrite coordinates with no undo. `NaN`/`Infinity` from a bad form value did the same.

**Solution:** `apps/partner/app/sites/[id]/inventory/actions.ts#adjustItemSpacing` rejects `!Number.isFinite(factor) || factor <= 0` with `{ status: 'error', errors: ['Spacing factor must be a positive number'] }` as its first statement — before `requireSiteOwner` and before any Prisma read. `moveParcel` / `moveItems` guard their lat/lng targets the same way (`Number.isFinite`, 'Invalid move target'), and `syncChairsWithLayout` validates `ChairConfig` (`rows >= 1`, `seatsPerRow >= 1`, `price >= 0`) right after auth. Pinned by `actions.test.ts` (`adjustItemSpacing — factor guard`, `syncChairsWithLayout — ChairConfig validation`).

**Prevention:** Any new action that takes a multiplier, delta or coordinate from the client validates it with `Number.isFinite` (+ sign/range) up front and returns the `{ status: 'error', errors }` shape — a coordinate-corrupting write is irreversible for the operator. Add the guard test next to the existing `describe` blocks in `actions.test.ts`.

## Parcel / group operations

### 2026-06-13: Seat number encoding & reversal action
tags: entities=inventory-item,parcel,seat-number,seat-label · files=apps/partner/app/sites/[id]/inventory/actions.ts,apps/partner/app/sites/[id]/inventory/geometry.ts,packages/schematic/src/grid.ts,packages/data/src/seat-label-db.ts · track=030

**Problem:** Operators need to flip seat numbering direction without moving beds. Re-running the grid generator with a flipped flag repositions beds, because `syncChairsWithLayout` matches existing items to generated cells **by `number`**.

**Solution:** `apps/partner/app/sites/[id]/inventory/actions.ts#reverseParcelNumbering(siteId, group)` fetches only `{ id, number }`, delegates the remap to the pure `apps/partner/app/sites/[id]/inventory/geometry.ts#reversedNumbers`, writes all updates in one `prisma.$transaction([...])`, then calls `recomputeSeatLabels(siteId)` (`packages/data/src/seat-label-db.ts#recomputeSeatLabels`) so the derived `parcel/row/seq` address follows.
- Number encoding is `Number(`${group}${rowNum2}${seatNum2}`)` in `packages/schematic/src/grid.ts#generateChairGrid` (`@repo/schematic/grid`); row prefix = `String(number).slice(0, -2)`, seat suffix = last 2 digits. `reversedNumbers` groups by prefix, sorts, maps position `i` to the suffix at `n-1-i`.
- Single pass, no temp-offset: `InventoryItem.number` has **no** uniqueness constraint (`@@index([siteId, number])` only). The unique key is `@@unique([siteId, parcel, row, seq])` on the derived address — anything that rewrites *those* columns directly must go through `recomputeSeatLabels` or stage with temp values.
- Pairing/grouping is by item `id` (`sunbedGroupId`), not number, so units survive relabelling. The manage grid's intra-pair gap is position-based (`packages/floor-core/src/grid-helpers.ts:95`, `pos % 2`), not number-parity, so reversal has no cosmetic side effect there any more.

**File placement rule:** `inventory/actions.ts` = bulk/group geometry + numbering ops (`syncChairsWithLayout`, `moveParcel`, `moveItems`, `rotateSelection`, `adjustItemSpacing`, `reverseParcelNumbering`, `reverseParcelOrientation`). `inventory/parcel-ops.ts` = unit/parcel ops shared with the AI assistant (`rotateUnit`, `rotateParcel`, `applyParcelConfig`, `setSeatsStatus`). `inventory/geometry.ts` = pure, Prisma-free helpers (unit-tested). `sites/[id]/inventory-actions.ts` = per-item CRUD (`createInventoryItem`, `saveInventoryItemProperties`, `saveInventoryItemSchematicLocation`, …).

**Prevention:** Before adding a "relabel in place" action, check `InventoryItem` in `packages/data/prisma/schema.prisma` for which columns are unique (`pairId`, `(siteId, parcel, row, seq)`) and decide single-pass vs temp-offset from that; put the pure remap in `geometry.ts` and the DB write in `actions.ts`.

## Map & drag-and-drop

### 2026-06-14: Sunbed unit members resolve from sunbedGroupId — no pairId readers remain
tags: entities=sunbed-group,inventory-item,rotation,drag · files=apps/partner/app/sites/[id]/inventory/useSunbedEditing.ts,apps/partner/app/sites/[id]/inventory/parcel-ops.ts,apps/partner/app/sites/[id]/inventory/view.tsx,apps/partner/app/sites/[id]/schematic/view.tsx · track=021,030

**Problem:** Rotate/drag handlers in both editors originally found "the partner" via the `pairId` scalar (`pairId ?? pair?.id ?? pairedBy?.id`), so N-member `SunbedGroup` units only co-moved one bed. The first fix (2026-06-14) resolved members client-side (`inventory.filter(i => i.sunbedGroupId === …)`) with a pairId fallback; that fallback has since been retired (track 021 P1) and rotate moved server-side (track 030).

**Solution — current shape:**
- **Rotate:** `apps/partner/app/sites/[id]/inventory/useSunbedEditing.ts#rotateSingle(itemId, delta)` calls `apps/partner/app/sites/[id]/inventory/parcel-ops.ts#rotateUnit`, which loads the unit's members by `sunbedGroupId` (excluding `status: 'pool'`) and either `rotateSelection`s them or rotates the single bed in place. Both `inventory/view.tsx#handleRotateSingleItem` and `schematic/view.tsx#handleRotateSingleItem` are one-liners into this hook — the client never picks ids. The same `rotateUnit` is what the AI assistant uses.
- **Schematic drag:** `apps/partner/app/sites/[id]/schematic/view.tsx#handleItemDragEnd` still resolves co-movers client-side from `sunbedGroupId` and saves each via `saveInventoryItemSchematicLocation` with the same delta (multi-selection drags go through `moveItems` instead).
- **Maps drag:** `apps/partner/app/sites/[id]/inventory/view.tsx#handleMarkerDragEnd` is parcel-level — `moveParcel(siteId, item.group, lat, lng, item.id)` with an **absolute target + anchor id**; the server computes the delta from the DB row (track 020 drag-jump fix, see the contract comment on `moveParcel`). No per-pair follow logic there.

**Prevention:** `grep -rn 'pairId ??' apps/partner` must stay empty — a hit means someone re-introduced a legacy pair reader. New "act on a unit" features call `rotateUnit`-style server ops in `parcel-ops.ts` rather than resolving members in the view; the `parcel-ops.*.test.ts` files are where the member-resolution tests live.

### 2026-06-14: SchematicRenderer co-move and pair highlight both key on groupId
tags: entities=schematic-item,sunbed-group,drag · files=packages/schematic/src/types.ts,packages/schematic/src/SchematicRenderer.tsx,apps/partner/app/sites/[id]/schematic/SchematicCanvas.tsx · track=021

**Problem:** The shared renderer's "partner follows the dragged item" logic was keyed on the domain-specific `pairId`. Once `SunbedGroup` became the source of truth for "items that move together", the renderer needed a domain-agnostic key.

**Solution:** `SchematicItem.groupId?: string | null` in `packages/schematic/src/types.ts` — "items sharing a non-null `groupId` move together on drag (outside a multi-selection)". `apps/partner/app/sites/[id]/schematic/SchematicCanvas.tsx` fills it from `item.sunbedGroupId`; `SchematicItem` no longer carries `pairId` at all, and the pair highlight is `isPaired = !!item.groupId` in the renderer (so groupId drives **both** co-move and highlight).

**Two drag sites in `SchematicRenderer.tsx` — update both or preview and commit diverge:**
1. `handleUp` (pointer-up) — commits `pendingItemDrops` for the dragged item plus `coMoverIds`.
2. The render-time IIFE — computes `dragCoMoverIds` / `isDragCoMover` / `followDrag` for the live preview offsets.

**Tables are a no-op by construction:** `packages/table-reservations-ui/src/partner/TableLayoutEditor.tsx` and `packages/table-reservations-ui/src/consumer/FloorMapPicker.tsx` never set `groupId` (grep-verified), so the field being optional keeps them unchanged.

**Prevention:** When extending renderer drag behaviour, grep `SchematicRenderer.tsx` for both `pendingItemDrops` and `followDrag` to find the two sites. Keep the renderer domain-agnostic — map domain ids to `groupId` in the consuming canvas, never inside `packages/schematic`.

### 2026-06-17: Mutating inventory actions end with revalidatePath('/sites')
tags: entities=inventory-item,server-action,cache,site-context · files=apps/partner/app/sites/[id]/inventory/actions.ts,apps/partner/app/sites/[id]/inventory-actions.ts,apps/partner/app/sites/[id]/inventory/parcel-ops.ts,apps/partner/app/sites/[id]/inventory/actions.test.ts

**Problem:** `syncChairsWithLayout` created/rearranged chairs but did not call `revalidatePath`, unlike every per-item action in `inventory-actions.ts`, so the server-rendered site context could serve the pre-mutation inventory until the next navigation. The omission recurred as a bug report in two sessions.

**Solution:** `apps/partner/app/sites/[id]/inventory/actions.ts#syncChairsWithLayout` now ends with `recomputeSeatLabels(siteId)` + `revalidatePath('/sites')`; `actions.test.ts` (`syncChairsWithLayout — calls revalidatePath after mutation`) pins it with a `vi.mock('next/cache')` spy. The convention across the surface: every action in `sites/[id]/inventory-actions.ts` and `inventory/parcel-ops.ts` revalidates `'/sites'` on success. The remaining bulk ops in `inventory/actions.ts` (`moveParcel`, `moveItems`, `rotateSelection`, `adjustItemSpacing`, `reverseParcel*`) do **not** — their callers in `inventory/view.tsx` `await` the action and then call the scoped `refreshItems(selectedItemIds)` (track 020: a full-site `refresh()` was ~5.8 MB per rotate) or `refresh()`, which is the client-side equivalent.

**Prevention:** A new mutating action either calls `revalidatePath('/sites')` before returning `{ status: 'ok' }` (required when any server component may read the result, and for anything the AI assistant can invoke) or is documented as refresh-on-client like the `actions.ts` bulk ops. Mock `next/cache` in the unit test and assert the call, as the existing `describe` does.
